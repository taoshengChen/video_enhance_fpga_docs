# Revision History Manager

此技能旨在自动化维护设计文档的版本管理章节。

## 专家指令

当用户要求更新某个 spec 的修订历史时，请严格执行以下步骤：

### 1. 差异获取 (Research)
- **路径切换（核心预检）**：由于本项目包含多个子仓库，**必须**先 `cd` 进入目标文件所在的具体目录。严禁直接在根目录执行 `git diff`，否则会因 Git 仓库边界限制而无法抓取到任何变更信息。
- 执行 `git diff <file_name>` 获取未提交的更改。
- 如果工作区干净，询问用户是否需要对比 `HEAD~1`（上一次提交）。

### 2. 变更提取 (Strategy)
- 分析 `diff` 内容，忽略格式/空格等琐碎变化。
- 提取功能规格、参数调整、接口定义等实质性变更。
- 按照 Markdown 列表格式生成简洁的变更描述。

### 3. 表格更新 (Execution)
- **表格定位与容错**：搜索 `# 2 修订历史` 或包含“修订历史”字样的章节。
    - 如果未找到表格：**必须**在该章节下新建一个标准 Markdown 表格，并默认当前版本为 `V1.0`。
- **提取当前版本**：从表格最后一行（忽略分隔线和空行）的第一列提取版本号。
    - 如果提取失败或格式不符（如非 `Vx.y` 格式）：默认当前版本为 `V1.0`。
- **强制交互 (ask_user)**：**必须且严禁跳过**调用 `ask_user` 询问用户。即使差异微小，也需由用户决定版本归属。
    - **选项设计**：
        - **选项 A (Append)**：使用当前版本号 `[Current]`，在末尾追加变更描述。
        - **选项 B (Suggest)**：使用建议版本号 `[Next]`（当前版本末位 +1），新建一行。
        - **选项 C (Custom)**：由用户手动输入。
- **逻辑分支处理**：
    - **同版本追加**：定位到表格最后一行，在“修订描述”列末尾使用 `<br />` 追加变更。
    - **新版本插入**：获取系统当前日期（格式 `YYYYMMDD`），在表格末尾插入新行。
- **执行原子化修改**：使用 `replace` 工具更新文件。

## 约束
- 必须保留现有的表格格式（对齐方式、分隔符）。
- 修订描述中如果包含多项，使用 `<br />` 进行换行以保持 Markdown 表格美观。
